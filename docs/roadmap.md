## Модель развёртывания

| Сценарий | Решение | Статус |
|---|---|---|
| Один клиент, один сайт, свой сервер | Одна установка (`make -C infra up`) | Работает |
| Один клиент, несколько сайтов на одном сервере | **Мультисайт в одной установке**: одна админка, одна БД, сайт резолвится по домену | Не поддерживается (фаза 3) |
| Разные клиенты на независимых серверах | **Дистрибуция**: версионированные готовые образы, одна установка на клиента | Частично — образ собирается на сервере клиента (фаза 2) |

Изоляция разных клиентов обеспечивается **разными установками**, не кодом. Мультисайт рассчитан на сайты одного владельца: граница доверия внутри установки — `canScope` (`editor` видит только свой сайт).

Не поддерживается и не планируется: несколько независимых установок на одном сервере за общим reverse proxy.

## Фаза 1 — фундамент (1–2 недели)

Цель: безопасность, корректность и защита от регрессий до роста функциональности.

### Баги

- [x] **Email-уведомления о заявках никогда не отправлялись.**
  Причина: `apps/web/server/utils/notify.ts` читал `site.settings.smtpHost` через публичный Payload API без токена, а поля `settings.*` доступны на чтение только `owner`. Исправлено: отправка перенесена в `apps/admin/src/utils/notify.ts`, вызывается afterChange-хуком на `form-submissions` (`overrideAccess: true`).
- [x] **`make -C infra new-site` вводил в заблуждение.** Раньше советовал поднять второй compose-проект на том же сервере — падает на конфликте портов (Caddy `80/443`, admin `3001`). Цель переписана: печатает, что новый сайт = новый сервер (сценарий не поддерживается, см. «Модель развёртывания»).
- [x] `env_file: ../.env` в `infra/docker-compose.prod.yml` был захардкожен в трёх местах (плюс пять раз в `Makefile`). Параметризовано одной переменной `ENV_FILE` (default `../.env`), можно переопределить: `make -C infra up ENV_FILE=../.env.staging`.
- [x] **`settings.analyticsId` нигде не использовался на web.** Подключён: поле стало публично читаемым (не секрет, в отличие от smtp-полей), `apps/web/app/utils/analytics.ts` (`yandexMetrikaTag`) строит тег счётчика Яндекс.Метрики, `layouts/default.vue` вставляет его в `<head>` через `useHead`, когда ID задан и валиден (только цифры).

### Безопасность

- [x] Первый пользователь в пустой БД создавался без auth и без явного `role: owner` становился `editor` — в системе не оставалось владельца. Исправлено: `beforeChange`-хук `users` (`apps/admin/src/utils/first-user.ts`) принудительно ставит `owner` первому пользователю независимо от переданных полей. Остаточный риск (не устранён, задокументирован в runbooks/prod.md): self-register в пустой БД всё ещё анонимный — кто первый создаст пользователя, тот и владелец.
- [x] `smtpPass` хранился в БД открытым текстом. Зашифрован: field-level хуки на `Sites.settings.smtpPass` (`apps/admin/src/utils/field-encryption.ts`) — AES-256-GCM, ключ — SHA-256 от `PAYLOAD_SECRET` (свой новый секрет не заводили: `PAYLOAD_SECRET` уже обязательный 32+ символа деплой-секрет). Обратная совместимость: нешифрованные (старые/dev) значения при чтении возвращаются как есть, перешифровываются при следующем сохранении — миграция данных не нужна.
- [x] Тест draft-фильтра: публичный API без токенов → утечка черновиков раньше ничем не была покрыта. Решение (вместо HTTP+БД интеграционного теста — сознательный выбор, см. PR): дублированная в `pages.ts`/`posts.ts` access-логика вынесена в чистую `publishedOnlyReadAccess()` (`apps/admin/src/access/site-scope.ts`), юнит-тесты покрывают все ветки (owner/анонимный/анонимный с `draft=true`/`status=draft`/editor по сайту).

### Качество / CI

- [x] GitHub Actions CI: `test` + `build` (postgres-сервис, `pnpm -r build`).
- [x] ESLint (единый конфиг на монорепо) + `lint` в CI. Один `eslint.config.mjs` в корне: `typescript-eslint` везде, `eslint-plugin-vue` (`flat/essential`, без стилистики — в репо нет Prettier) для `apps/web`, `eslint-plugin-react` + классические `react-hooks` правила для `apps/admin`. `no-explicit-any` выключен (Payload/Nuxt код на нём держится); Nuxt auto-imports (`useHead`, `useSite`, `mediaUrl` и т.п.) — вручную заданный список globals, `@nuxt/eslint` не подключали.
- [x] `typecheck` (`tsc --noEmit` / `nuxt typecheck`) во всех workspace + в CI. Первый прогон нашёл настоящие баги, не только типовой шум: `useSeoMeta({ canonical })` — не существующий у `useSeoMeta` ключ (canonical — это `<link>`, не `<meta>`), тег canonical никогда не рендерился на всех 4 публичных страницах — перенесено на `useHead({ link: [...] })`; и `allowedVariants()` могла вернуть пустой список для темы, ссылающейся на несуществующий id варианта (опечатка в конфиге) — `resolveVariant` в этом случае резолвил бы `variant: undefined`. Оба зафиксированы тестом. `apps/web` держит `typescript@^5` — `vue-tsc@3.3.11` пока несовместим с TypeScript 7 (`ERR_PACKAGE_PATH_NOT_EXPORTED` на `typescript/lib/tsc`).
- [x] CI-проверка миграций: `migrate` на чистой БД + `migrate:generate` (авто-ответ "нет" на "создать пустую миграцию?", если дрейфа нет) → `git status --porcelain` на `src/migrations/` — если появился новый файл, схема разошлась с миграциями, job падает. Проверено вручную (throwaway Postgres) на обоих сценариях: нет дрейфа → 0 новых файлов; добавил тестовое поле в `Sites` → файл создаётся немедленно, без интерактивного вопроса.

## Фаза 2 — дистрибуция и продукт (1–2 месяца)

### Дистрибуция (разные клиенты — разные серверы)

Цель: установка и обновление у клиента без сборки на его сервере и без ручных шагов.

- [x] **Один универсальный образ web.** `NUXT_PUBLIC_MEDIA_BASE` передавался как build-arg — домен клиента был зашит в образ, пересборка при смене домена. Перенесено в `web.environment` (`infra/docker-compose.prod.yml`), derives из `SITE_DOMAIN`, переопределяемо через `.env` без пересборки. Технически Nuxt/Nitro уже поддерживал runtime-override публичного `runtimeConfig` через `applyEnv` (проверено в скомпилированном `nitro.mjs`: ищет `NITRO_PUBLIC_*`, потом `NUXT_PUBLIC_*`) — проблема была только в том, что compose никогда не прокидывал переменную в `environment:` контейнера, только в build-arg. Изменений в `nuxt.config.ts` не потребовалось.
- [x] Аудит build-time значений в `infra/docker/*.Dockerfile`. `admin.Dockerfile` — ARG/ENV нет вообще, `next build` не трогает БД по-настоящему (проверено: собран Docker-образ без единой env-переменной, `ECONNREFUSED` при попытке достучаться до Postgres поймана внутри Next/Payload, страницы просто не пререндерятся статически — build успешен). `web.Dockerfile` — остался один ARG (`PAYLOAD_URL=http://admin:3001`), но это internal DNS-имя compose-сети, одинаковое для всех клиентов, не client-specific — печь в образ можно. По ходу нашёл и убрал два мёртвых runtime `environment: { PAYLOAD_URL }` (в compose у `web`, и `ENV PAYLOAD_URL=...` в финальной стадии Dockerfile) — не работали вообще: Nitro's `applyEnv` при override публичного/приватного `runtimeConfig` ищет `NUXT_`/`NITRO_`-префикс, а не голое имя переменной; проверено эмпирически (сборка с одним значением, запуск с другим — сервер стучался по build-time значению). Работало «случайно», потому что build-time и intended runtime значения совпадали.
- [x] Публикация образов `admin`/`web` в GHCR из CI по git-тегу (`vX.Y.Z`). Новый job `publish` в `.github/workflows/ci.yml` — триггерится на push тега `v*.*.*`, `needs:` все остальные job'ы (lint/typecheck/test/migrations/build), т.е. образ публикуется только после зелёного CI. Тегируется как `<tag>` и `latest`. `GITHUB_TOKEN` (без доп. секретов) — `permissions: packages: write` на уровне job'а. Потребление образов клиентом (`image:` вместо `build:` в prod-compose) — следующий пункт, не делал.
- [x] Prod-compose для клиента на `image:` вместо `build:`; версия — одна переменная в `.env` (`IMAGE_TAG`, default `latest`). Нюанс, который всплыл по ходу: опубликованный `admin`-образ — Next.js standalone (`output: 'standalone'`), в нём нет `node_modules/payload/bin.js`, `ts-loader`, `src/migrations` (standalone-трассировка берёт только то, что нужно HTTP-серверу, CLI-путь Payload не видит). `migrate`-сервис не может работать на этом образе — добавлен третий publish-таргет, `admin-migrate` (та же `admin.Dockerfile`, стадия `build`, весь монорепо + full `node_modules`, заметно больше рантайм-образа). Проверено: реальный прогон `pnpm --filter @siril/admin migrate` внутри собранного `--target build` образа против живого Postgres — все 8 миграций применились. `make -C infra up` теперь `--pull always` вместо `--build` (билдить больше нечего). Полная процедура обновления с бэкапом — следующий пункт, не делал.
- [x] Процедура обновления: бэкап БД → `IMAGE_TAG` в `.env` → `docker compose pull && up -d` (миграции уже применяются сервисом `migrate` при старте, `admin` не стартует, пока `migrate` не завершится успешно). Описано в [runbooks/prod.md §4.1](runbooks/prod.md), включая откат при упавшей миграции (восстановление бэкапа до отката тега образа).
- [x] `CHANGELOG.md` с явной пометкой breaking-изменений и ручных шагов миграции. [Keep a Changelog](https://keepachangelog.com/ru/1.0.0/) формат, версии = git-теги `vX.Y.Z`. Ретроактивно восстановил `v0.1.0` (первый релиз, по факту всей истории коммитов до тега) и `v0.2.0` (переход prod-compose на GHCR-образы, PR #17) — оба тега на самом деле уже существовали в репозитории (`git tag -l`), просто без файла. Задокументировал единственное найденное breaking-изменение постфактум: `v0.2.0` требует сетевого доступа сервера к `ghcr.io`.
- [x] Установщик/чеклист первой установки: генерация `PAYLOAD_SECRET`/`POSTGRES_PASSWORD`/`PURGE_TOKEN`, создание owner. Новый скрипт `infra/scripts/init-env.sh` (`make -C infra init SITE_DOMAIN=...`) — копирует `.env.example` → `.env`, подставляет случайные секреты через `openssl rand -hex`, отказывается перезаписать существующий `.env`. По ходу нашёл: `PURGE_TOKEN` до этого не было даже в чеклисте вручную заполняемых ключей (`docs/runbooks/prod.md` §1) — дефолт `dev-purge-token` из `.env.example` мог случайно уехать в прод. Также `POSTGRES_DB_URI` теперь генерируется с тем же паролем, что и `POSTGRES_PASSWORD` (раньше — два места, куда пароль нужно было вписать вручную и не разъехаться). Чеклист-версия §1 в runbooks/prod.md объединяет генерацию секретов и создание owner (было раньше отдельно, §2.1) в одну последовательность шагов. Проверено: скрипт и `make init` (тем же аргументом, что и make-таргет) прогнаны во временной директории — генерация + отказ перезаписи существующего `.env` оба ведут себя как задумано.

### Продукт для контент-менеджера

Цель: снять трение в ежедневной работе с сайтом.

- [x] **Preview черновиков по ссылке** (первый этап; живое обновление без reload — следующим шагом). Использован встроенный механизм Payload `admin.preview` (`GeneratePreviewURL`, `node_modules/payload/dist/config/types.d.ts:159-164`) — Payload сам передаёт `token`, JWT текущего редактора, в опции колбэка; вместо отдельного shared-secret (`PREVIEW_TOKEN`, обсуждали изначально) preview-роут форвардит этот JWT в `Authorization: JWT <token>` при запросе `draft=true` к Payload REST. Т.к. это тот же пользователь, что и в админке, существующий `access.read` (`publishedOnlyReadAccess`, `apps/admin/src/access/site-scope.ts`) отрабатывает БЕЗ изменений — owner видит любой драфт, editor видит драфты своего сайта, посторонний/просроченный токен → 401 у Payload → preview 404. Новых access-веток и новых секретов не добавлено.
  - `apps/admin/src/utils/preview-url.ts` — чистая функция генерации URL (протестирована, TDD), подключена в `admin.preview` `pages.ts`/`posts.ts`.
  - `apps/web/server/api/preview/{page,post}.get.ts` — фетчат `draft=true` с форвардингом JWT; `apps/web/app/pages/preview/{page/[...slug],post/[slug]}.vue` рендерят тем же `BlockRenderer`/`RichText`, что и публичные страницы, плюс `<meta name=robots content=noindex>`.
  - Важная находка по ходу: HTML-кэш (`apps/web/server/middleware/cache.ts`) кэшировал по пути БЕЗ учёта query — второй заход на `/preview/page/<slug>` без токена получил бы закэшированный черновик первого захода. Добавлено исключение `/preview` из кэша (как уже было для `/api` и `/media`).
  - Проверено вживую (реальный admin+Postgres, throwaway контейнер, не dev-instance): сохранён черновик с изменённым title → кнопка «Предпросмотр» открывает `/preview/page/<slug>?token=<JWT>` → рендерится ИМЕННО черновик (`_status: draft`, новый title в `__NUXT_DATA__`); публичный `/about` в это же время отдаёт опубликованную версию; поддельный токен → Payload отклоняет JWT → анонимный доступ к драфту заблокирован (`publishedOnlyReadAccess`) → 404, черновик не утёк.
  - Не сделано (следующий шаг, отдельная задача): `admin.livePreview` + postMessage-bridge для обновления без reload — под Vue готового SDK у Payload нет (только `@payloadcms/live-preview-react`), нужен свой listener на `@payloadcms/live-preview` (vanilla).
- [ ] **Медиа в S3-совместимом хранилище** (`@payloadcms/storage-s3`) — опционально, по env; локальный volume остаётся дефолтом для простых установок. Провайдер-агностично (AWS/R2/Yandex Object Storage/self-hosted) — решение принято, не начинали код.
  Разведка (см. `node_modules/@payloadcms/storage-s3/dist/*.js` в момент разведки):
  - `Media` коллекция (`apps/admin/src/collections/media.ts`) сейчас завязана на локальный диск: `beforeOperation`-хук делает dedup по файлам на диске, `afterChange` физически перемещает (`fs.rename`) файл в `<site>/` после записи — костыль вокруг того, что путь нельзя было задать до аплоада. Для S3-режима эти хуки не нужны вообще.
  - У плагина есть готовый механизм: `prefix` — отдельное авто-инжектируемое поле документа (не часть `filename`!). S3-ключ = `${prefix}/${filename}` (`buildStoragePathData`). Значит для S3 нужно ставить `data.prefix = String(siteId)` в хуке, `filename` НЕ трогать (в отличие от локального режима, где `<site>/` сейчас вшивается в сам `filename`).
  - `generateURL()` строит `${endpoint}/${bucket}/${prefix}/${filename}` — прямой URL на бакет, НЕ проксируется через admin `/api/media/file/...`. Значит `apps/web/app/utils/media.ts` (`mediaUrl()`) обязательно нужно менять — сейчас он игнорирует `doc.url` и сам собирает путь через `/api/media/file/`. Эмпирически проверено (реальный admin + Postgres): в локальном режиме `doc.url` уже абсолютный (`${PAYLOAD_URL}/api/media/file/...`) — можно safely предпочитать `doc.url`, если есть, с фолбэком на текущую сборку для объектов без `url` (обратная совместимость с текущими тестами).
  - Побочная находка: `docs/runbooks/prod.md` не включает `PAYLOAD_URL` в обязательные prod-переменные — если оставить дефолтный (`localhost:3001`), `doc.url` в проде будет неверным. Сейчас это не всплывает, т.к. web строит URL сам через отдельный `NUXT_PUBLIC_MEDIA_BASE`; после перехода на `doc.url` это станет реальной зависимостью — надо будет явно задокументировать/проверить.
  - Живой E2E-тест S3-пути (аплоад в реальный MinIO/S3-совместимый сервер) не сделан: `minio/minio` в Docker Hub deprecated (переехал на AIStor, лицензируемый — «All S3 operations are denied» без лицензии), альтернативы (LocalStack и т.п.) не пробовали. Нужно решить, чем поднимать S3 для тестов (CI и локально) при возврате к задаче.

### Мультисайт в одной установке (один клиент — несколько сайтов)

Схема данных уже почти готова: `sites` (уникальный `domain`), обязательная связь `site` у pages/posts/categories/forms/form-submissions, `site-content` — одна запись на сайт, `canScope` для `editor`. Не готов web-слой — он рассчитан на один сайт в БД.

- [x] Резолв сайта по `Host` на web; все публичные запросы (`/api/page`, `/api/site`, блог, sitemap, submit формы) скоупятся по сайту. `apps/web/server/utils/site-resolve.ts` (`pickSiteByHost`, с тестами) — точное совпадение по `Sites.domain` (регистронезависимо), fallback на единственный сайт при несовпадении (совместимость с текущими установками, где `domain` не обязателен/не уникален); при 2+ сайтах и несовпадении — `null` → 404.
  - Ключевая находка (проверено эмпирически, не предполагалось): SSR-фетчи Nuxt (`$fetch('/api/site')` из `useAsyncData` внутри Vue-страницы) НЕ прокидывают исходный `Host` внутреннего запроса — сервер видит `localhost` вместо реального хоста браузера. `useRequestHeaders`/`getRequestHost` внутри API-роута тут бесполезны. Рабочий путь — `useRequestURL().host` на уровне САМОЙ Vue-страницы (SSR+клиент, официальный композabl Nuxt), хост передаётся явным query-параметром `?host=` в каждый внутренний фетч. Роуты, куда браузер бьёт напрямую (`sitemap.xml`, `submit.post.ts`) — им это не нужно, `getRequestHost(event)` у них корректен и так.
  - Правки: `site.get.ts` (кэш стал `Map<host, ...>` вместо одного глобального значения — иначе один сайт закэшировал бы данные под хостом другого), `page.get.ts`, `post/[slug].get.ts`, `posts.get.ts`, `sitemap.xml.ts` (base URL теперь из `Site.domain` резолвленного сайта, а не из статического `SITE_DOMAIN`), `submit.post.ts` (форма ищется `where[slug]` + `where[site]`, не только по slug).
